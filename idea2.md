## 🧠 Приоритет 1: Прорывные (сразу дают ценность)

### 1. Пул ключей с ротацией
Сейчас — один ключ на провайдера. Сделать **пул ключей** с round-robin / least-usage / random стратегией. Если один ключ выжег квоту — автомат на следующий.

### 2. Free Tier — маршрутизация с учётом квот
Зашить лимиты бесплатных тарифов (Groq: 14 400 req/day, Gemini Flash: 1500 req/day, OpenRouter `:free`: 50 req/day на модель, NVIDIA: 40 req/min). Роутер сам направляет запросы так, чтобы не превысить дневной лимит ни по одному ключу.

### 3. Автоматический failover при 429
Ловишь `429 Rate Limit` или `quota exceeded` — роутер мгновенно переключает на другой провайдер/ключ. Уже есть `FallbackDecorator`, но его надо прикрутить к роутеру на уровне ключей, а не только адаптеров.

### 4. Режим "FreeFirst" для SLA
Новый SLA-режим: **сначала бесплатные модели**, переход на платные только когда все бесплатные ключи уткнулись в лимит. Идеально для твоей модели использования.

### 5. Интеллектуальная цепочка fallback'ов
Пример: агент → Groq Llama → Gemini Flash → OpenRouter `:free` → NVIDIA NIM. Если один провайдер лёг, следующий в цепочке подхватывает.

## 🎯 Приоритет 2: Умная маршрутизация

### 6. Дебатная маршрутизация
Участников дебатов раскидывать по **разным провайдерам и разным ключам** — максимум параллелизма и никакой один ключ не блокирует весь дебат.

### 7. Request queuing с приоритетом агентов
PriorityQueueDecorator уже есть, но его надо связать с роутером: агенты с высоким приоритетом получают быстрые ключи (Groq), фоновые задачи — медленные/бесплатные.

### 8. Балансировка по текущей латентности
Роутер учитывает **текущую latency** каждого провайдера в реальном времени. Если Groq вдруг тормозит — перекидываем на Gemini Flash.

### 9. Сессионная привязка (sticky sessions)
Все запросы одного агента/диалога идут через один и тот же ключ — консистентность ответов.

### 10. A/B тестирование провайдеров
CanaryRouterDecorator уже есть. Расширить: для каждого агента можно задать "кандидат-провайдер", собирать статистику успешности.

## 📊 Приоритет 3: Мониторинг и квоты

### 11. Дашборд квот
Визуальная панель: "Groq: 12 340 / 14 400 req today (86%)", "Gemini: 890 / 1500" и т.д. Красные маркеры при приближении к лимиту.

### 12. Автоматическое отключение ключа при исчерпании квоты
При 100% использовании дневной квоты ключ помечается как `quota_exhausted`, запросы перенаправляются на другие ключи/провайдеры. На следующий день сброс.

### 13. Автоматическое понижение модели при нагрузке
При приближении к лимиту — downgrade: Gemini Pro → Gemini Flash → Gemini Flash-Lite. Вместо отказа — чуть хуже, но работает.

### 14. Трекинг срока жизни бесплатных ключей
У бесплатных ключей OpenRouter часто есть expiry. Добавить поле `expiresAt`, показывать warning за 24 часа до истечения.

Сейчас только regex-проверка префикса. Добавить **мгновенный health check** при добавлении ключа (запрос к /models или минимальный промпт).

## 🔄 Приоритет 1: Роутинг и балансировка

### 21. **Сложностная маршрутизация (complexity-based routing)**
Агентский запрос → если простой (суммаризация, перевод) → Groq/Gemini Flash. Если сложный (код, reasoning) → Gemini Pro / OpenRouter платные. Семантический роутер уже есть в `SemanticRouterDecorator`, но его надо соединить с `RouterService`.

### 22. **Virtual API Keys**
Как в LiteLLM/Bifrost: создаёшь виртуальный ключ для каждого агента или дебата, а реальные ключи провайдеров живут только в ядре. При компрометации одного виртуального ключа — всё остальное работает. Можно удобно банить конкретного агента.

### 23. **Адаптивный exploration bonus**
Сейчас exploration bonus = `sqrt(log(totalRequests) / successCount)`. Усложнить: если ключ долго не использовался — повышать ему приоритет, чтобы "разогреть" и проверить, жив ли.

### 24. **Pre-emptive rate limit avoidance**
Анализировать заголовки `x-ratelimit-remaining`, `x-ratelimit-reset` из ответов провайдеров и заранее снижать нагрузку на ключ, не дожидаясь 429.

### 25. **Provider-aware request splitting**
Контекстно-зависимые запросы (с длинным контекстом, до 1M токенов) отправлять на Gemini (у него бесплатно 1M контекст). Короткие — на Groq (скорость).

## 🤖 Приоритет 2: Агенты и дебаты

### 26. **Оптимизация system prompt кэширования**
Если system prompt одинаковый у всех агентов — кэшировать его как префикс (Gemini и OpenRouter поддерживают prompt caching, дают скидку 50-75%).

### 27. **Агентский профиль провайдера**
Для каждого агента вести свою историю: "Agent-A на Groq отвечает быстрее, на Gemini — точнее". Роутер учитывает персональную статистику.

### 28. **Debate-specific provider mixing**
В дебатах каждый участник должен иметь `unique` провайдера/модель для максимального разнообразия мнений. Роутер гарантирует: если 4 участника — 4 разных провайдера, или хотя бы разные ключи.

### 29. **Graceful degradation при превышении квоты**
Если все бесплатные ключи исчерпали дневную квоту — не фейлить запрос, а ставить в очередь до сброса квоты (например, до полуночи). Или предлагать пользователю добавить новый ключ.

### 30. **Self-healing ключей**
Если ключ упал с 401 (invalid) — автомат снимаем с ротации. Если ключ упал с 429 — ставим таймер на `Retry-After` секунд, потом пробуем снова. Если снова 429 — увеличиваем паузу (exponential backoff).

## 💰 Приоритет 3: Free Tier Management

### 31. **Free tier budget per provider**
Дашборд с жёсткими лимитами: Groq — 14 400 req/day, Gemini — 1500 req/day, OpenRouter `:free` — 50 req/day/model, NVIDIA — ~500 req/hour. Роутер сам следит, чтобы не превысить.

### 32. **Provider ranking по free tier**
Ранжировать провайдеров по "ценности" для бесплатного использования. Например: Gemini > Groq > NVIDIA > OpenRouter `:free` > HuggingFace. Более ценные провайдеры получают приоритет для важных агентов.

### 33. **Free model discovery**
Автоматически подтягивать список бесплатных моделей с OpenRouter (модели с суффиксом `:free`) и обновлять их в UI. Сейчас список моделей статический.

### 34. **Multiple free accounts round-robin**
Для каждого провайдера завести N бесплатных аккаунтов. Роутер распределяет нагрузку по round-robin, увеличивая суммарный лимит в N раз.

### 35. **Usage pattern prediction**
ML-модель предсказывает, когда закончатся бесплатные квоты, и рекомендует оптимальное распределение запросов.

## 🛡️ Приоритет 4: Безопасность и мониторинг

### 36. **Slack/Telegram alerts при исчерпании квоты**
Webhook-уведомления: "Groq key-3 исчерпал дневную квоту (14 400/14 400). Запросы перенаправлены на Gemini."

### 37. **Audit log всех запросов**
Лог: какой агент → через какой ключ → какой провайдер → результат. Для отладки, кто и куда жжёт квоту.

### 38. **API key usage heatmap**
Визуальная карта: почасовая/подневная загрузка каждого ключа. Видно, когда упираемся в лимит, и можно скорректировать.

### 39. **Rate limit budget per agent**
Агент-шумомеру даём лимит 100 req/day. Основному агенту — 5000 req/day. Если агент превышает — его запросы ставятся в очередь низкого приоритета.

### 40. **Zero-trust key validation**
Перед каждым запросом валидировать, что ключ ещё активен (не revoked, не expired). Не полагаться только на `checkHealth` раз в 5 минут.
