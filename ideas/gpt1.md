# Архитектурный аудит Admin/UI Layer

Провести глубокий аудит проекта с фокусом на принцип:

> «Система принадлежит одному владельцу-администратору.
> Внутренних скрытых настроек, скрытых режимов, hardcoded-only возможностей или “кода ради кода” быть не должно.
> Всё, что влияет на поведение системы, должно быть доступно через Admin UI, меню, панели, разделы настройки или хотя бы через отдельный “Lab / Experimental” раздел.»

## Основная задача

Проверить:

* можно ли через админку реально управлять всеми модулями системы;
* существуют ли скрытые настройки, hidden flags, внутренние сервисы или параметры, недоступные из UI;
* есть ли функциональность, которая существует только в коде и не имеет точки управления в интерфейсе;
* есть ли “мертвые” архитектурные слои, которые выглядят красиво, но не используются пользователем;
* есть ли decorators/services/modules, которые невозможно включить, отключить, настроить или наблюдать из интерфейса;
* есть ли маршрутизация, SLA, fallback, pools, providers, queues, debates, policies, health checks, governance, observability или security-механизмы, не представленные в UI.

---

# Ключевой принцип проекта

Проект НЕ является enterprise SaaS.

Проект — это:

* локальная AI-OS,
* personal control plane,
* single-owner system.

Следовательно:

* пользователь = администратор = владелец системы;
* допустимо выводить даже сложные и “не production-like” настройки;
* допустимо иметь “опасные” или низкоуровневые панели;
* допустимо показывать технические детали;
* допустимо иметь разделы “Lab”, “Experimental”, “Advanced”, “Raw Controls”.

Главное:

> Ничего важного не должно быть скрыто внутри кода без возможности управления.

---

# Требуется проверить отдельно

## 1. Menu Coverage Audit

Проверить:

* покрывает ли текущее меню все ключевые subsystem;
* есть ли сервисы без UI-entrypoint;
* есть ли backend-модули, до которых невозможно добраться из интерфейса;
* есть ли настройки, доступные только через env/config/code.

---

## 2. Hidden Logic Audit

Найти:

* hidden defaults;
* hardcoded policies;
* скрытые fallback chain;
* скрытые routing rules;
* скрытые quotas/limits;
* скрытые provider mappings;
* скрытые experimental flags;
* “магические” значения внутри сервисов.

Для каждого:

* указать файл;
* объяснить влияние;
* предложить способ вывода в UI.

---

## 3. Dead Architecture / Code-for-Code Audit

Найти:

* абстракции без практического применения;
* decorators/services без UI-интеграции;
* системы, которые невозможно наблюдать или настраивать;
* “архитектуру ради архитектуры”;
* overly enterprise-подходы без пользы для single-user режима.

---

## 4. Admin Control Completeness

Проверить:

* можно ли из UI:

  * включать/отключать providers;
  * менять pools;
  * менять routing;
  * управлять quotas;
  * смотреть pressure/load;
  * управлять fallback chains;
  * смотреть key health;
  * видеть events;
  * видеть reasoning router decisions;
  * менять SLA/policies;
  * управлять debates/agents.

Если чего-то нет:

* указать;
* предложить UI placement.

---

## 5. Observability Accessibility

Проверить:

* доступны ли logs/events/metrics через UI;
* есть ли скрытая telemetry;
* есть ли background decisions без объяснения пользователю;
* можно ли видеть:

  * почему был выбран provider;
  * почему сработал fallback;
  * почему key был disabled;
  * почему request ушёл в queue.

# Новый обязательный раздел UI

Добавить отдельный раздел:

# PATTERNS

Структура:

* Patterns

  * Google
  * Groq
  * NVIDIA
  * OpenRouter

Назначение:

* хранение архитектурных паттернов;
* заметок;
* инсайтов;
* best practices;
* ссылок;
* форумных находок;
* routing ideas;
* quota strategies;
* provider-specific behavior;
* experimentation backlog.

Это должен быть не просто markdown viewer, а knowledge accumulation layer для дальнейшей разработки системы.

---

# Важно

Даже если:

* настройки сложные,
* выглядят “слишком техническими”,
* не подходят под enterprise UX,
* перегружают интерфейс,

их всё равно нужно выводить наружу хотя бы в:

* Lab,
* Advanced,
* Experimental,
* Raw Control Panels.

Принцип проекта:

> “Никакой скрытой магии.
> Всё, что влияет на систему — наблюдаемо и управляемо.”

---

# Требуется результат аудита

1. Список subsystem без UI.
2. Список hidden logic.
3. Список “code-for-code” архитектуры.
4. Список того, что нужно вывести в Admin UI.
5. Предложение новой структуры меню.
6. Предложение структуры раздела Patterns.
7. Оценка текущего уровня “Admin Controllability”.
